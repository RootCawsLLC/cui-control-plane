# ADR 0002 — The 110 are a requirement index, not 110 control records

**Status:** accepted · **Date:** 2026-08-19

## Context

The implementation plan calls for "110 control records for NIST SP 800-171 Rev 2." Taken literally
that means one house control per requirement, one-to-one.

That reading conflicts with the layer-split discipline, and the conflict is not academic. Requirement
3.5.3 (multifactor authentication) applies inside the CUI boundary. The enterprise also runs MFA on
corporate IT, with a different owner, a different threat model, and a different failure mode. A
one-to-one mapping forces those into a single record — which is precisely the munged control that
makes an SSP indefensible under review, and it is the mechanism by which a single failure in
corporate IT would cost points in an SPRS score it has nothing to do with.

The reverse pressure is just as real: several requirements are legitimately served by one control,
and one control legitimately serves several requirements.

## Decision

Split the two ideas apart.

- **`reference/nist-800-171r2.index.yaml` is the assessment target.** 110 requirement identifiers,
  fourteen families, generated by `scripts/gen-requirement-index.mjs` so the family counts are
  provable rather than typed. It holds identifiers and nothing else.
- **`controls/` is the control inventory.** Our controls, our assertion text, split by layer.
- The relationship is **many-to-many in both directions**, expressed as `crosswalk[]` edges on the
  control records, and reported by `ccp coverage`.

Coverage is therefore something computed and stated, never implied by a count of files.

## Why Rev 2 and not Rev 3

CMMC is legally pinned to **Rev 2** — 32 CFR 170.2 incorporates the February 2020 revision by
reference. NIST published **Rev 3** in 2024, and `usnistgov/oscal-content` ships an OSCAL catalog
for **Rev 3 only**. NIST publishes OSCAL for the revision that does not legally apply.

Consequences:

1. Build against Rev 2. Rev 3 is a watch item, not a migration.
2. Anyone doing OSCAL-based CMMC work must author their own catalog. This repository does
   (`src/oscal/catalog.mjs`). The FATHOM5 community 800-171 content is the best available starting
   point for the requirement layer, and is community-sourced — diff it against the official Rev 2
   text before trusting it, and do not vendor it here.

## Consequences

- `ccp coverage` will report a large uncovered count for a long time, and it enumerates every
  uncovered identifier rather than summarising. That list *is* the Phase 1 backlog. A repository
  that reported a comfortable number here would be lying about a greenfield build.
- Requirements mapping to zero controls are either a genuine gap or a scoping decision nobody wrote
  down. Both need a profile-level tailoring statement, which is what the O2 Profile carries.
- The index carries no requirement text. See ADR 0006.
